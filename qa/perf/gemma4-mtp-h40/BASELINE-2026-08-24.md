# Windows H40 baseline — Gemma 4 26B-A4B MTP, 2026-08-24

First matched measurement of the MTP lane on the frozen 48-token fixture. Three arms,
same binary, same request, same environment. Receipts in `runs/`.

**These absolute tok/s figures are not promotable.** Available RAM was 5.6–6.8 GiB
against a ~9.6 GiB touched set, and free RAM at load moves this lane by more than most
changes under test. The **ratios and the per-round wall split are** the result; they are
structural and do not move with host RAM.

| arm | decode tok/s | alpha | acceptance | rounds | assistant ms/round | verifier ms/round | misses / committed token | ids |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| plain | **5.46** | — | — | — | — | — | 78.2 | reference |
| mtp-k1 | 3.60 | 0.96 | 100.0% | 24 | 159 | 394 | 78.9 | **exact** |
| mtp-k8 | 2.69 | 5.86 | 91.1% | 7 | 996 | 1,545 | 77.7 | **exact** |

## 1. There is no alpha failure

The handoff carried alpha 1.18 against "the ~6 needed to break even". On this workload
alpha is **5.86**, against the Metal campaign's 6.00 at the same K. Acceptance is 91.1%,
and across the whole run there is exactly **one** rejected draft:

```
round  pos  bonus   drafted -> accepted   assistant_ms  verify_ms   first reject
  0    104    100    0 ->  0                     0          747     (bootstrap, no drafts)
  1    105  45518    8 ->  8                  1196         4033
  2    114 236764    8 ->  8                  1251         1465
  3    123    751    8 ->  4                  1274         1664     draft 2802 vs target 1550
  4    128   1550    8 ->  8                  1226          981
  5    137   2861    8 ->  8                  1235         1333
  6    146   4464    5 ->  5                   791          590
```

One content-boundary miss in 45 drafts, the same character as the Metal campaign's single
remaining miss. At K=1 the drafter is right **24 times out of 24**.

The earlier 1.18 was a different workload, not a defect: alpha is a property of the
prompt, and this fixture is a near-verbatim struct rewrite, which drafts well. The
directive's step 3 — "attribute the alpha failure before optimizing compute" — is
answered by there being nothing to attribute. **The lane's problem is entirely cost.**

Two suspects the directive named are also cleared, without spending a run on either:

- **Target parity is not the cause.** Windows and the Mac emit the same 48-token answer
  apart from one 3-token insertion at index 4 (Mac opens a ``` fence, `rust`, LF; Windows
  goes straight to `pub`), after which both streams are identical for 44 tokens. Note the
  direction: the Mac's *drafter* proposed 9430 (`pub`) and its target overrode it — the
  Windows target picks 9430 itself, so the Mac's known content-boundary miss cannot occur
  here. Windows target parity is *helping* alpha, not hurting it.
- **Proportional RoPE is already correct.** `apply_rope` pairs `(d, d+256)` over 64 active
  pairs, matching the Mac's `FULL_ROPE_ACTIVE_PAIRS = FULL_HEAD_DIM / 8` fix that was
  worth +9.8% there, with a committed test pinning it.

## 2. The verify pass is (K+1) sequential decodes — exactly, measurably

Cost per **verified position**:

| | positions per round | verifier ms/round | ms per position |
|---|---:|---:|---:|
| plain decode step | 1 | 183 | 183 |
| mtp-k1 | 2 | 394 | 197 |
| mtp-k8 | 9 | 1,545 | 172 |

Flat across a 4.5× change in batch width. `verify_chunk_logits` reaches
`prefill_chunked_inner` with `ChunkLogits::EveryPosition`, which is layer-major but
**token-serial inside each layer** — `for li { for t { forward_token_impl(li..li+1) } }` —
so a K=8 round performs 9 full scalar decodes and runs the Q6_K head 9 times. There is no
batching win in the current "batched verify" at all.

The expert-cache column is the corroborating negative: **77.7 / 78.2 / 78.9 misses per
committed token** across the three arms. A verify batch neither pays an expert-union
penalty nor saves any weight traffic, because it never amortizes a weight read across the
batch. That also refutes, for this lane, the Metal campaign's expert-union objection to
batched speculative verify — the union cost simply is not being incurred.

## 3. The drafter is 36× the Mac's, and fixing it alone is not enough

The CPU f32 assistant costs **~155 ms per draft step** (159 at K=1, 6,973 ms / 45 drafts
at K=8). The Metal device chain was 34 ms for a whole K=8 round, i.e. ~4 ms per step.
The module doc's claim that a GPU port of the drafter "buys nothing" is a Metal result and
does not transfer: here the drafter is 41% of a speculative round.

Break-even arithmetic against this run's own plain lane (183 ms/token, alpha 5.86):

```
budget per round   = (1 + 5.86) x 183  = 1,255 ms
actual per round   = 155 x 8 + 1,545   = 2,785 ms      2.22x over
drafter on device  =   4 x 8 + 1,545   = 1,577 ms      1.26x over   <- still loses
verifier at 2 steps=   4 x 8 +   366   =   398 ms      0.32x        -> ~17 tok/s
```

Both fixes are needed and their order is forced: **the verifier is the larger term and the
only one that can turn the sign.** A device drafter on its own leaves the lane slower than
plain decode.

## 4. Round 0 is a wasted round

The bootstrap round drafts nothing and still pays a 747 ms verify, because prefill does
not hand back the target's final normalized hidden. On a 7-round generation that is one
round in seven forfeited outright — worth more here than on longer generations, and it is
the cheapest item on the list.

## 5. Two things the stderr says that the receipt did not

**The whole-run decode rate hides a large warm-up.** The plain arm's forward-rate curve
over successive 8-forward windows was

```
[0-7]=2.50  [8-15]=4.73  [16-23]=6.71  [24-31]=9.09  [32-39]=7.29  [40-46]=9.68
```

— 5.35 forwards/s across the whole run against **8.60 steady** over the second half. The
handoff already identified the cause (layer-major prefill leaves the expert arena holding
the LAST layer's union, so decode re-accumulates a cross-layer working set over ~24
tokens) and measured it as "~12% of the all-decode average" on a 128-token generation. On
a **48-token** request that warm-up covers half the run and costs **38%**. `plain` here is
therefore 5.46 tok/s whole-run and 8.60 steady, and the two are not interchangeable.

`arms/plain-tokenmajor.json` is the probe: token-major prefill walks all 30 layers per
token, so it leaves a cross-layer arena. If the curve flattens, the warm-up is a
prefill→decode handoff artifact and worth fixing in the eviction policy; if it does not,
it is decode's own working set and the door is closed.

**No host expert tier is in play.** Both runs logged

```
[ghost] host expert tier skipped: ~2.5-3.1 GiB auto budget would cover under 40% of the
12399 MiB routed payload
[sser] expert-residency cache ON: capacity 889 experts (requested 1000, VRAM-fit 889;
3104 MiB free)
```

So every miss is an NVMe read, and the VRAM arena holds 889 of 3,840 records (23%). The
arena is sized by *free VRAM*, which is what makes VRAM elsewhere — the 646 MiB Q6_K head,
the f16 KV — a throughput lever and not just a footprint one.

**Correction to an earlier reading of these numbers.** Dividing lifetime misses by
generated tokens gave "78 misses per decoded token", which implied ~131 ms of NVMe per
token and a storage-bound round. That was wrong: the counters are lifetime-since-load, and
a layer-major prefill over a 104-token prompt touches most of the 12 GiB payload once, so
it owns the great majority of those 3,754 misses. Decode's real rate is the difference
against the prefill boundary, and `prefill_sser_mark` now records that boundary so the
receipt reports `decode_misses_per_token` directly instead of leaving it to arithmetic
that is easy to get wrong.

## 6. Where a decode step actually goes (`CAMELID_SSER_PROFILE=1`, plain arm)

```
MoE CPU-side totals: dense-MLP 169 ms, router 829 ms, expert-loop 8773 ms
  expert-loop split: hit-path 177 ms, miss-path 42 ms, rest(prep+dtoh+sync) 8555 ms
  blind spots: router fence 2821 ms, blocking .cghost reads 8307 ms
               (11.83 GiB at 1.53 GB/s); rest-minus-storage 248 ms
  tied head: 295 ms (~646 MiB read per token regardless of routing)
  miss provenance: 2258 first-touch / 1496 re-fetch = 39.9% churn;
                   mean re-fetch age 7222 lookups (~30.1 tokens at 240/token)
```

**Storage is the run.** 8.3 s of blocking `.cghost` reads against a ~13 s generate. Kernel
time is not close: the whole expert hit path is 177 ms and the Q6_K head 295 ms (6.1 ms per
token, ~106 GB/s effective — it is VRAM-resident and cheap).

Splitting that 11.83 GiB by phase, using the prefill/decode counter mark:

| | records | bytes | wall | rate |
|---|---:|---:|---:|---:|
| prefill (unbuffered path) | 2,176 | 6.78 GiB | ~3.6 s | ~1.9 GB/s |
| decode (mapped path) | 1,578 | 4.92 GiB | ~4.7 s | **~1.04 GB/s** |

Decode's ~1.04 GB/s sits between this drive's 0.74 GB/s cold-fault rate through a map copy
and its ~1.9 GB/s on explicit reads. Solving the blend puts roughly **one third** of decode
misses in the page cache and **two thirds** faulting cold.

That matters because the decode read path is mapped *on purpose*: `GhostFile`'s comment
records a paired 13.0% regression from routing decode reads to `read_exact_at`, on the
premise that "most reads hit the page cache". The premise is host-state-dependent — it
holds when free RAM can cover a useful share of the 12 GiB payload and fails when it
cannot. `arms/plain-decodebulk.json` and `CAMELID_GEMMA4_GHOST_DECODE_BULK_READS` exist to
A/B that on the host in question. The knob defaults **off**, i.e. to the measured-better
setting, because one profile on one degraded host is not grounds for flipping a default
that was established with a paired ABABAB.

**Churn is 39.9%, and its age is the arena's turnover time.** 1,496 of 3,754 misses are
re-fetches of experts the cache already held, wanted again ~30 tokens later. The arena
holds 889 records and decode misses 32.9 per token, so it turns over in ~27 tokens. Those
two numbers matching is the signature of a working set slightly larger than the arena —
capacity, not policy. That is consistent with the handoff's closed eviction-policy row
(LRU 68.9% against Belady-OPT 90.3% on the real trace: real headroom, no implementable
policy captured it) and it means the levers are arena size or bytes per record, both of
which are hard here.

## 7. The decode read path was costing 2x — paired result

Acting on §6: force the decode phase onto the unbuffered read path and A/B it alternating,
three pairs, cooled between runs.

| pair | `plain` (mapped) | `plain-decodebulk` | steady delta |
|---|---:|---:|---:|
| 1 | 10.10 | 13.74 | +36.0% |
| 2 | 9.99 | 13.72 | +37.4% |
| 3 | 10.50 | 13.76 | +31.0% |

**Mean +34.8% steady, sign consistent across every pair.** Whole-run decode went
6.13-6.21 → 12.35-12.37 tok/s, a clean **2×**; decode wall 7.73-7.83 s → 3.88-3.89 s. The
scatter within an arm is tiny (12.35 / 12.35 / 12.36), which is what a real effect looks
like on a box that can otherwise manufacture phantom ones.

Three things say this is the mechanism and not a coincidence:

- **Demand faults collapsed**: 1,537,920 → 452,969 pages, ~70% fewer. That is exactly the
  ~816-faults-per-record map degeneration going away.
- **Miss counts are byte-identical** at 1,578 in every run. Nothing about caching,
  routing, or residency moved — only how the same bytes were fetched.
- **Token ids are exact in all six runs.** The read path cannot change arithmetic, and the
  gate proves it did not.

The default is now **auto** rather than flipped: `decode_bulk_reads` takes the map only
when available RAM at load covers the whole routed payload, and the unbuffered path
otherwise. That keeps the earlier paired result (13.0% regression from positioned reads on
a warm host) correct in the regime where it was measured, because that result's stated
premise — "most reads hit the page cache" — is exactly the condition the rule tests.
`CAMELID_GEMMA4_GHOST_DECODE_BULK_READS=0/1` forces either side, and
`arms/plain-decodemap.json` keeps the old behaviour as a standing control: if it ever wins
on a starved host, the threshold is wrong.

Note what this does *not* claim. It is one host state (7.4 GiB available, 12.4 GiB
payload) and one prompt. The rule is a mechanism, not a tuned constant, and the 16 GiB
product constraint means this host state is the common one rather than an edge case.

## 8. The host expert tier was refused on a premise that no longer held

Decode was *still* ~68% storage after §7, so the next question was residency. Auto-sizing
refuses any tier covering under 40% of the payload, and its stated reason is that a small
tier "starved the OS page cache that was previously absorbing those reads". Unbuffered
decode reads bypass the page cache — so that rationale is void in exactly the regime §7
selects, and the gate was being asked with stale premises.

Sized from the churn data rather than guessed: re-fetches arrive ~7,222 lookups after
eviction, i.e. about 990 intervening misses, and ~960 records is 3 GiB.

| pair | `plain` (no tier) | `plain-hosttier3g` | steady delta |
|---|---:|---:|---:|
| 1 | 13.70 | 18.73 | +36.7% |
| 2 | 13.68 | 18.80 | +37.5% |
| 3 | 13.75 | 18.76 | +36.5% |

**+36.9% mean, sign consistent, token ids exact in all six runs.** A single 4 GiB probe
went further still — steady **20.32**, decode wall 3.00 s, tier hit rate 12.2% → 18.1% —
so the curve is not flat at 3 GiB.

The gate is now relaxed to **20% coverage only when available RAM cannot cover the
payload**, and left at 40% otherwise. On this box that admits the 3,224 MiB tier auto
already wanted (`min(spare, payload, installed/5)`), which is the size measured above. The
installed-RAM cap and the 3 GiB reserve are untouched: those are safety limits, not
calibration, and the 4 GiB probe only cleared them because it was an explicit override.

### A defect in the rule, caught by its own log line

The first build of the auto rule printed

```
[ghost] decode reads: unbuffered (279 MiB available cannot cover the 12399 MiB routed
payload, so a mapped miss faults cold)
```

**279 MiB.** The rule was resolving lazily at the first prefill, by which point the tier had
pinned 3.1 GiB and the resident core was up — so it was comparing the RAM left *after our
own allocations* against the payload. That answers "unbuffered" on every host alive,
including one with 128 GiB, which is not the mechanism and would have silently discarded
the warm-host case the whole rule exists to preserve.

Both rules now read `ghost_host_ram_at_load()`, sampled once before anything is pinned. The
decision on this box is unchanged (8,317 MiB against a 12,399 MiB payload), but it is now
the decision the documentation describes.

### Correction: the ~4 s load cost was the harness, not the product

This section first reported that the tier "fills synchronously at load, so first-token
latency grows by ~4 s", and proposed filling it asynchronously. Both were wrong, and the
arms were at fault.

The load-time stripe (`prefill_from_ghost`) is **off by default**: auto enables it only when
the tier covers 40% of all expert records, and at 960 of 3,840 it covers 25%. But every arm
here carried `CAMELID_GEMMA4_GHOST_TIER_PREFILL=1`, inherited from the perf handoff's
reproduce block, where it was a harmless no-op because no tier existed to stripe. Once the
gate change built a tier, that stale line started forcing 3 GiB of index-ordered reads at
load — a cost the shipping default never pays.

Measured paired ×3, forced-on against default-off:

| | load | steady tok/s | tier decode hits / storage reads |
|---|---:|---:|---|
| stripe forced on | 12.1–13.1 s | 14.5 / 16.3 / 16.1 | 484 / 1,094 |
| stripe off (default) | **8.5–8.8 s** | 16.4 / 16.3 / 16.6 | **484 / 1,094** |

The decode-phase tier hit rate is **identical to the record**, because the stripe fills
experts 0..31 by index — unrelated to routing — and prefill's 2,176 first-touch inserts
displace it before decode asks anything. It is pure cost, which is why it is auto-disabled
at this coverage and why `arms/plain-tierstripe.json` now exists only to keep the receipt.

True shipping defaults: **load 8.4 s**, steady 16.8 at 8.6 GiB available, 48/48 exact. The
tier's real load cost is the ~1.4 s to page-lock 3 GiB, against no tier at all. There is
nothing to make asynchronous.

## 9. Why the current scalar MTP lane loses, and what would change that

Re-measured at K=8 on the improved baseline. The verifier fell **1,545 → 512 ms/round**, a
3.0× improvement bought entirely by §7 and §8 — right at the ~490 ms the directive named
as the bar. And it still loses, decisively: 5.46 tok/s against plain's 18.8 steady.

The reason is one number:

| | misses per **committed** token |
|---|---:|
| plain | 32.3 |
| mtp-k8 | 32.3 |

**Identical.** A verify batch reads exactly the same storage bytes per emitted token as
plain decode does. That is not a coincidence, it is the geometry: the K tokens in a batch
are the same K tokens plain decode would have processed one at a time, so their expert
union is ~K× one token's, and the batching saving and the union penalty cancel out.

Speculative decode's premise is that verifying K tokens costs about what decoding one
costs. That holds when the weights are resident — the Metal campaign runs 2,100 hot records
in unified memory and sees 78.9 misses per *round* where this lane sees 222. It does not
hold when experts stream from NVMe, because then the cost is bytes fetched, and batching
does not reduce bytes fetched.

Ceiling, using this run's own numbers: storage is ~373 ms of the 512 ms verify round. Give
the drafter a perfect device chain (Metal's ~4 ms/step → 32 ms/round) *and* a batched
verify that removes every non-storage cost, and a round is 405 ms for 6.86 tokens = 59
ms/token = **16.9 tok/s**, against plain's 53 ms/token = **18.8 tok/s**.

**Correction after the current-main/Mac audit:** that ceiling treats bytes as fixed wall
time, but the current verifier discovers and reads each distinct miss serially. This same
Windows drive measured independent whole-record reads at 1.04 GB/s at depth 1 and 2.42
GB/s at depth 4 (`src/ghost.rs`); splitting one record remained a regression. A true K-wide
verifier exposes a layer's distinct expert union before compute, so it can issue four
whole-record reads concurrently. Applying the measured QD4 ratio to the 373 ms storage
term projects ~160 ms storage; keeping all 139 ms non-storage work plus a 32 ms device
drafter gives ~331 ms/round, or **~20.7 tok/s** at alpha 5.86 before routed-GEMM savings.
That is a projection, not a result, but it reopens MTP: the required order is exact K-wide
union planning → four-way distinct-record I/O → batched HtoD/GEMM, then the CUDA drafter.

Directive steps 4–7 — the CUDA assistant chain and `verify_batch_moe` — remain a large
build, but the QD4 result changes their order. The prerequisite is a true K-wide verifier
that discovers the exact per-layer expert union before issuing I/O. That makes four-way
distinct-record reads possible and then feeds batched HtoD/GEMM. More residency still
helps every arm, but misses do not have to reach zero before batching can win.

The landed `attention_sw_batched` / `q4_0_gemm_routed` / `q4_1_gemm_routed` kernels are
therefore kept as prerequisites. The next throughput work is the K-wide verifier and its
four-reader union path; the host tier remains a supporting cache rather than the blocker.

## 10. What the tier is actually doing, and a hypothesis it refuted

The tier's lifetime hit rate of 13.1% looked like failure, and the obvious explanation was
pollution: a layer-major prefill is a streaming scan that inserts 2,176 first touches, so it
should flush the tier before decode asks it anything. That predicted decode ≈ 0% and prefill
holding all the hits. Phase-split counters say the reverse:

```
host tier: 493 hits lifetime | DECODE 484 hits / 1094 storage reads = 30.7%
```

Prefill accounts for **9** of the 493. A streaming scan of first touches cannot hit, which
is why the lifetime rate is low — and it is not hurting either, because those inserts are
displaced by decode's own before decode needs them. **No admission change is warranted**,
and building the scan-resistant scratch path would have been effort spent on a defect that
is not there. The `SserCache` miss-provenance classifier and this split cost nothing when
profiling is off and between them turned a plausible story into a measured one.

So the tier converts 30.7% of decode's arena misses into RAM hits, and decode's real storage
traffic is **1,094 reads = 3,490 MiB**, not the 5,034 MiB an arena-miss count implies. The
receipt reported the latter as "storage" until this run; it now separates
`decode_storage_reads` from `decode_misses`, because a tier hit never touches the disk.

### The remaining lever is capacity, and it has a cliff

Re-fetch age is ~7,222 lookups ≈ **990 intervening misses**. The tier holds **960** records.
Those two numbers being within 3% of each other is the whole story: the tier is sized just
below the reuse distance it exists to span, which is the worst place to be. It also explains
the forced 4 GiB probe (1,230 records, clear of 990) reaching steady 20.32 against 3 GiB's
18.7–18.8 — not a smooth capacity curve, a threshold.

Auto picks `min(spare, payload, installed/5)`; on this box the **cap** binds at 3,224 MiB,
not spare (4,953 MiB).

### Crossing it: the cap is now regime-dependent too

The divisor's own rationale names three things that squeezed a 5.98 GiB tier down to "tens
of MiB available": WDDM commit, the mapped common weights, and **the `.cghost` page cache**.
The third is absent once decode reads are unbuffered — that payload is not being cached at
all — so one of the three pressures the fifth was sized against is gone, exactly as with the
coverage gate in §8. The cap is therefore a **quarter** in the unbuffered regime and a fifth
everywhere else, which selects 4,030 MiB (~1,220 records) on a 16 GiB host: clear of the
~990-miss reuse window, and still far below the 5.98 GiB tier that actually failed.

Paired ×3, forced-fifth control against the new default:

| | tier decode hit rate | decode storage | steady tok/s |
|---|---:|---:|---:|
| cap = ⅕ (974 records) | 30.7% | 3,490 MiB | 15.81 / 15.66 / 14.40 |
| cap = ¼ (~1,220 records) | **41.6%** | **2,941 MiB** | 16.51 / 16.47 / 16.34 |

**+7.7% steady, sign consistent**, ids exact in all six runs. The mechanism is visible rather
than inferred: arena misses are **identical at 1,578**, so nothing about VRAM residency or
routing moved — only how many of those misses RAM could serve, 484 → 656. Storage fell 16%
in step with it.

Safety held on both sides: host delta ranged +17 to −14 MiB available with **zero pagefile
growth** in every run, and the `available − reserve` term still binds independently, so a
host that is merely large but busy does not get a big tier out of this. `arms/plain-tiercap5`
keeps the fifth as a standing control — if it ever wins, the quarter is too big.

One definition now drives both rules and the read path: `ghost_decode_reads_unbuffered`. If
they could disagree, the tier would be sized for one regime while the reads ran in the other.

## 11. What this does not measure

- Absolute throughput at a settled host. Re-run at ≥ 10 GiB available before quoting.
- Anything paired. Every number above is a single run; thermal drift on this box has
  manufactured a phantom 1.8× before. Comparisons here are between arms whose *structure*
  differs by more than any plausible drift (2.2×, and a flat per-position cost), not
  between close numbers.
- Cold cache. Load was 25.8 s cold and 7.7–8.1 s warm; decode figures are warm.

## 12. Post-main bounded-context result (2026-08-25)

After merging current `main`, the frozen request was run in three adjacent `plain` /
`plain-kv192` pairs at the 6.5 GiB admission floor. All six runs reproduced the committed
Windows token ids exactly:

| arm | decode tok/s | steady tok/s | resident experts | decode misses |
|---|---:|---:|---:|---:|
| plain | 11.07 / 11.64 / 11.48 | 14.90 / 15.16 / 14.86 | 889 | 1,578 |
| plain-kv192 | 12.43 / 12.30 / 12.03 | 16.50 / 16.88 / 16.07 | 967 | 1,226 |

The bounded context won every pair by **10.8%, 11.4%, and 8.2% steady** (**10.1% mean**).
It frees enough VRAM for 78 more expert records and cuts arena misses by 22.3%. Storage
reads move only 922 → 899 because the larger VRAM arena also changes which reuses reach
the host tier; the improvement is therefore not a simple storage-byte ratio.

This is a benchmark-safe fixture, not a 4,096-context shipping default: unlike the Mac
growable-KV fixture, `CAMELID_GEMMA4_GHOST_CUDA_CONTEXT=192` is a hard request cap. Runtime
generation now clamps to the remaining CUDA context and the MTP verifier rejects an
out-of-range batch instead of touching past KV.

One exact `mtp-k8-kv192` receipt reached **3.55 tok/s** at alpha 5.86. Its 7 rounds spent
8,404 ms in the CPU assistant and 5,068 ms in the scalar verifier, confirming the next
work remains the K-wide verifier/four-reader path and then the CUDA assistant.

## 13. Scalar distinct-record QD4 is exact but negative (2026-08-25)

The caller half of the unbuffered-reader experiment now reserves every distinct miss in a
layer's top-8 route, lets up to four positioned readers fill separate page-locked tier
slots, restores router order, and then submits the existing batched HtoD path. The code is
opt-in through `CAMELID_GEMMA4_GHOST_BATCH_READS`; the default remains unchanged.

One candidate, its adjacent control, and a crossed resident-hit-overlap probe used release
binary SHA-256 `3F18D095B9D09F99F1C1D3394DE951189C79CA1517318F26F506BA20983F45A5`.
All three reproduced the 48 Windows token ids exactly and had identical residency and
traffic: 967 resident experts, 1,226 decode arena misses, 327 tier hits, and 899 storage
reads (2,868 MiB).

| arm | available RAM | decode tok/s | steady tok/s |
|---|---:|---:|---:|

### The resident-first split — the first structural overlap in the verify round

Nsight showed the round's storage wait and expert HtoD overlap **zero** compute: the
routed GEMMs fence on `expert_copy_done` for the *entire* union, so experts that were
already VRAM-resident wait for the 2–4 missing records per layer to stream from
tier/NVMe. The fix reorders the union residents-first (a pure renumbering —
`gemma4_reorder_union_residents_first`, pinned by a stable-permutation unit test), splits
the resolve into a touch phase and a fill phase, and launches the routed
GateUp→GeGLU→Down chain twice: the resident expert range is enqueued *before* the CPU
blocks on the missing experts' reads, the missing range after its copies land, as
contiguous sub-range launches of the same kernels (`launch_q4_0_gemm_routed_range`).
Bit-exactness is by construction — each expert's per-row fold still happens whole inside
exactly one launch, `token_offsets` values stay absolute so outputs land at identical
positions, and the weighted sum consumes router order — and is pinned on hardware by the
two-pass range case added to `q4_0_gemm_routed_matches_gemv`.

Opt-in `CAMELID_GEMMA4_MTP_RESIDENT_SPLIT=1` (strict 0/1). Paired ×3 on the composed K=7

| 3 | 23.56 | **25.64** | +8.8% |

## 17. Second wave (2026-08-26): two honest negatives, and where the wall actually is

Before building anything further, two candidate levers were killed **offline** with the
§14-era route trace (`…-trace` run, 4,560 `[route]` lines):

- **Tier eviction hybrids lose to MRU.** Simulating the exact traced demand sequence
  through the LFU arena + 1,218-slot tier: MRU 93.3 verify storage reads/round, LRU 140.9,
  every recency-protected hybrid 107–142. The sim's MRU figure matches the live receipts,
  so the ranking stands. Recency protection displaces the stable hot head MRU retains.
- **Cross-round route prefetch has almost nothing to prefetch.** Per-layer unions overlap
  74% round-over-round (85.5% over two rounds) — but the round's **disk reads are the
  unpredictable tail**: only 1–18% of them appear in the previous round's union (≤46% in
  two). The predictable experts are already served by tier+arena; storage is also already
  running at the drive's depth-4 ceiling during fills. The storage column is closed on
  this RAM/VRAM budget. (This also forecasts the Metal campaign's "cross-layer speculative
  expert prefetch" lever: same tail, same wall.)

Two levers were then built, A/B'd paired ×3 on the composed K=7 rsplit arm, and called
honestly:

- **On-device assistant draft chain — NULL.** `CAMELID_GEMMA4_MTP_DEVICE_DRAFT_CHAIN=1`
  keeps the argmax→next-embedding dependency on-device (Q6_K head-row gather, pinned
  bitwise by `q6k_row_gather_scale_matches_cpu_decode`; drafts drain in one round-end
  DtoH). Measured 25.74/26.16/26.09 vs 26.32/25.93/26.32 — sign flips; assistant wall is
  ~170 ms/request in both arms because the removed per-proposal syncs were waiting on
  kernels that had to finish anyway. Kept opt-in; the unconditional rope-upload hoist
  (4 uploads/round instead of 56) rides along as an inert refactor.
- **Routed-arena SoA (Step 05) — REGRESSION.** `CAMELID_GEMMA4_GHOST_ARENA_SOA=1`
  measured 25.69/25.76/25.83 → 22.32/22.96/23.11, verifier 281→316–327 ms/round, ids
  exact, misses identical. The CPU repack rides the QD4 read workers between
  read-completion and HtoD — ~30–50 ms/round of staging cost against a routed-GEMM
  kernel term nsys put at ~28 ms/round *total*. Kept default-off; a device-side
  post-copy permutation (~2.6 ms/round at VRAM bandwidth) is the variant that could
  flip the sign and would reuse these kernels and parity pins unchanged.

**The composed K=7 + resident-split arm therefore remains the standing best:
25.7–26.3 whole-decode tok/s across the day's twelve control runs** (~7.6–8.1 GiB
available, all token-exact).
