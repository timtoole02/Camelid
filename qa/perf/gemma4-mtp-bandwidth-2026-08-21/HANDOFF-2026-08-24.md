## The one fact to keep

The hybrid mapped-cold round did **not** cost 9 s because cold records are slow.
The unified decode command buffer is encoded before the GPU router runs, so it
cannot know the routed union and declares `active = 0..128` per layer — binding
30 x 96 = 2,880 no-copy mmap records, ~9.65 GiB, every round. **The cost is per
round, not per cold record.** Cutting mapped selections 94 -> 62 moved the round
9530 -> 9727 ms. Do not re-derive this from the miss counters; they mislead.

## Do not repeat these

- **`SLOT_POLICY=lru`** — 724 ms/round against 609 ms for the default LFU.
- **Prefetching from the previous round's routed union** — 435 ms / 15.74 tok/s
  against 306 ms / 21.52. Once the hot tier is sized to the union, last round's
  union is already resident, so the speculative pass fetches nothing
  (`wave_load` 0.2 ms) and only pays plan/publish churn. The residual reads are
  by construction the experts routed for the *first* time.
- **`DECODE_PROMOTION` / `MAPPED_RDADVISE`** — both inert against the real cost.
- **Reading `disk_time` as wall time** once the pooled fill is on: it is a sum
  over threads. Use `slot_filler`.
- **Sorting pooled record reads by source offset.** Two interleaved H2/H4 pairs
  kept the same 2,294 reads / 7.32 GiB and changed prefill filler by +0.4%; the
  decode swing reversed sign between pairs. The experimental switch was removed.
- **Raising hybrid minimum capacity to 64.** It reduced decode reads but did not
  produce a repeatable tok/s or end-to-end win and consumed more memory.
- **Anonymous fixed-64 as the throughput profile.** The correctly bounded C4
  run was exact but only 16.31 tok/s with 138.5 misses/round. An earlier C3 run
  did not set physical capacity at all: it allocated 2,640 records / 8.26 GiB,
  then collapsed under memory pressure. Do not use C3 as evidence for fixed-64.

## Where the round goes now

```
round ~300 ms = assistant 34 ms + verifier ~265 ms
  slot_wait ~120 ms   <- this IS gpu_busy: attn + router + shared MLP
  slot_filler ~100 ms <- record copies, GPU idle
  MoE + tail; final_wait 3 ms; encode 1 ms
GPU split: gateup ~62, qkv_o ~37, shared ~20
```

The fill cannot move earlier. Layer N's route needs layer N-1's output, so
GPU -> route -> fill -> GPU is a true dependency chain.

## Next, in the order I would take them

1. **Close the C5 reload gap with dynamic admission / shared record capacity.**
   Anonymous records sustain ~2.8 GiB/s, roughly 3.7x H2's mapped-to-hot copy
   rate, but C5 reloads 136.5 experts/round versus H2's 78.9. The per-layer
   profile is a static approximation of a global allocator; moving record
   capacity toward the currently wide layers without losing residency is the
   highest-upside path exposed by this A/B.
2. **Future-token prefetch.** The only way to hide the ~100 ms fill is a
   predictor that sees the next token — the MTP assistant's drafts are the
   candidate. Research, not an afternoon.
3. **GPU kernels** — gateup ~62 ms is the largest single term. Note the long
   history of sub-threshold results here (MMA, dense pre-unpack, exact-f32 MoE
   dots all measured and rejected; see `README.md` and the `*-no-go-*.md` notes).
4. **Prefill record churn.** Prefill is still the largest wall-clock opportunity,
   but the old diagnosis was wrong: current K=8 unions are bounded at 64, H2
   demand-promotes the exact union, and mapped readahead is zero. The 104-token
   prompt crosses 13 chunks and H2 still performs 2,294 record reads / 7.32 GiB,
   with ~3.96 s in `slot_filler`. Work on retention/admission across chunks or
   chunk geometry; do not optimize a nonexistent ~85-record mapped binding.

## Anonymous-record defect — resolved

The bad anonymous numbers came from an ordering violation, not bad weights. The
overlap path pre-encoded and committed the MoE command before the GPU router was
observed, the required records were filled, and the expert-to-slot table was
published. Missing entries silently behaved like dropped routes, producing fast
garbage. Anonymous record rounds now obey `route -> fill -> publish -> commit`
and fail closed if any layer reaches the end without routed-union evidence.

Two adjacent defects were fixed at the same time:

- hybrid mixed-table reuse is keyed by the published directory, physical versus
  canonical mode, and exact normalized active union, preventing stale cold
  fallback bindings;
- the anonymous LFU planner pre-pins every resident needed later in the current
  union and refreshes usage accounting even on all-resident rounds.

C4 and C5 both pass the frozen 48/48 token oracle. Every old anonymous-lane
throughput number produced before this fix remains invalid.

## FreeToken comparison

[FreeToken](https://github.com/FlashML-org/FreeToken) is the right provenance
for the overlap idea, but its safe prefill
scheme streams the *entire next expert layer* into two identity-indexed buffers;
compute waits on a ready event and buffer reuse waits on release. Its decode path
first obtains the real route, then loads missing experts, then executes GEMM. In
other words, it never commits route-dependent compute against an unpublished
table. Borrow the ready/release ownership invariant. Do not copy its full-layer
policy into Camelid: Gemma4 K=8 activates at most 64 of 128 experts per prefill
chunk, and the prompt repeats that work across 13 chunks.
