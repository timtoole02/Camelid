# Chat context meter evidence

Generated by `node scripts/capture-context-meter.mjs` against a running dev server
(`npm run dev`) on 2026-08-30, at 1440 x 900 in the dark theme, with a draft message
in the composer so the conversation row is non-zero.

- `01-panel-open.png`: the expanded breakdown on Llama 3.2 1B Instruct Q8_0 with its
  full 131,072-token window. The figures form one right-aligned column and sum to the
  ruled total (83 + 8,192 + 122,797 = 131,072). The verified-bound marker sits at 8,192
  and is described as a tested envelope, not a ceiling.
- `02-collapsed-chip.png`: the resting state in the composer status line — a percentage
  and a short bar, next to the existing readiness text.
- `03-small-window.png`: a model loaded at 4,096 tokens while the configured reply limit
  is the 8,192 default, so the reservation is clamped. The reply row is labelled
  `left for the reply` rather than `held for the reply`, `still free` is dropped because
  it is genuinely zero, and the chip turns amber. This is the state that exposed the
  clamped-reservation defect described in the PR: before the fix this same screen read
  `100% used, 4.1K / 4.1K` on an otherwise empty chat.

## Reproducing shot 03

The released binary these were captured against predates `active_context_length` on
`/health` and omits it, so the capture patches that one field in the page to the 4,096
a current server reports for a model loaded at that size. Everything else is the real
application against the real backend. The capture asserts the chip does not read
`100% used` and fails if it does, so this evidence cannot silently go stale.

The PNGs are dated review evidence, not pixel-golden tests. The arithmetic they show is
enforced independently by `npm run smoke:context-meter`; `SHA256SUMS` protects the
committed bytes.
